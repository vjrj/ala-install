# `la-docker-compose` — Docker Compose Deployment for Living Atlas Portals

## What is this?

`la-docker-compose` is an Ansible-based toolkit that deploys a full [Living Atlas](https://living-atlases.gbif.org/) portal using [Docker Compose](https://docs.docker.com/compose/), instead of installing services directly on virtual machines.

It works alongside the existing [ala-install](https://github.com/AtlasOfLivingAustralia/ala-install) toolkit — reusing its battle-tested configuration logic — while adding the orchestration layer needed to run everything in containers.

---

## Why build on ala-install instead of starting from scratch?

`ala-install` is a large, mature Ansible repository built by the [Atlas of Living Australia](https://www.ala.org.au/) team over many years. It encodes an enormous amount of accumulated knowledge:

- Hundreds of small technical decisions about how each service should be configured
- Nginx virtual host setups, SSL handling, service interconnections
- Database schema initialization, migration sequences, validation checks
- Internationalisation (i18n) package management
- Monitoring endpoint definitions

Throwing all of that away to rewrite it from scratch would be impractical and risky. It would mean duplicating thousands of lines of proven configuration, and then maintaining that duplicate independently — diverging from ALA's ongoing improvements.

**ALA itself continues to use `ala-install`** for many services, and is making a gradual, progressive transition to containers. `la-docker-compose` follows the same path: reuse the configuration logic from `ala-install`, add a thin Docker orchestration layer on top, and stay in sync with ALA's evolution.

In concrete terms, this means:

- Service configuration files (`/data/<service>/config/`) are generated by the same Ansible roles as in a VM deployment — the only change is that these files are mounted as Docker volumes into the containers instead of being read directly.
- Nginx virtual hosts, Gatus monitoring endpoints, and i18n packages are all generated by the same roles, with no duplication.
- When ALA updates a configuration template or adds a new service option, the change flows automatically into Docker deployments too.

The only code that lives exclusively in `la-docker-compose` is the orchestration layer: generating `docker-compose.yml` files, managing Docker volumes, and handling container-specific startup concerns.

---

## How does it relate to `la-docker-images`?

`la-docker-compose` does **not** build Docker images. That responsibility belongs to the separate [`la-docker-images`](https://github.com/living-atlases/la-docker-images) repository, which produces versioned, ready-to-run images for each ALA service. `la-docker-compose` simply references those images by version tag.

This separation of concerns means:

| Repository | Responsibility |
|---|---|
| `ala-install` | Service configuration, nginx, i18n, DB init logic |
| `la-docker-images` | Building and versioning Docker images (Java baked in) |
| `la-docker-compose` | Orchestration: compose files, volumes, deployment pipeline |

## Key features

### Multi-host deployments and progressive migration

A Living Atlas portal typically runs across multiple machines. `la-docker-compose` supports **mixed deployments**: some machines can run services in Docker Compose while others still run the same services on traditional VMs. This makes it possible to migrate services one at a time, without taking the portal offline.

Cross-machine communication is handled through Docker's `extra_hosts` mechanism, which works regardless of whether the target is a container or a VM.

### SSL certificate management

SSL certificates must be in place before any services can start. `la-docker-compose` handles this explicitly:

- Certificates are verified for existence and validity before the deployment proceeds.
- Both **production certificates** (from Let's Encrypt or your organisation's CA) and **self-signed test certificates** are supported.
- Certificates are shared with the nginx container via a named Docker volume (`la-site-certs`), so they can be renewed on the host without rebuilding containers.

### CAS authentication initialisation

Setting up CAS (the authentication system) requires a precise sequence of steps: starting the database containers, waiting for them to be healthy, initialising database schemas, running Flyway migrations, registering OIDC service definitions, and then starting the application. `la-docker-compose` automates this entire sequence, reusing the existing `cas5-dbs` initialisation logic from `ala-install` without modification.

### Database backups

A lightweight backup container runs on a schedule, producing dumps of MySQL, MongoDB, and PostgreSQL. Backups are written to `/data/docker-compose/db-backups/` on the host and can be enabled or disabled per deployment with `enable_db_backup: true`.

### Solr initialisation

Solr requires its collection configurations to be present before the first start. `la-docker-compose` copies the Solr config files from the `solrcloud_config` role in `ala-install` into a local init directory (`./solr/init/`), which the Solr container mounts and applies automatically on startup.

### Cassandra initialisation

The Cassandra schema (used by biocache for annotations and persistent queries) is taken from the `biocache3-db` role and placed in `./cassandra/init/schema.cql`. The Cassandra container executes this CQL script on first start if the database is empty.

Both Solr and Cassandra initialisation reuse the existing files from `ala-install` — no duplication, no drift.

### Email configuration

Two modes are supported:

- **Development mode** (`docker_mail_development_mode: true`): all outgoing email is captured by [Mailhog](https://github.com/mailhog/MailHog) and shown in a web UI. Nothing leaves the server. Useful for testing without affecting real users.
- **Production mode**: email is sent through [Postfix](http://www.postfix.org/) with relay to your organisation's SMTP server.

All services connect to the local mail container automatically — no per-service configuration is needed.

### Monitoring with Gatus

[Gatus](https://github.com/TwiNNatE/gatus) provides a real-time status dashboard showing which services are healthy. `la-docker-compose` generates the Gatus configuration automatically from the inventory — including services running on other machines in the cluster — so the monitoring view is always complete and up to date.

### Internationalisation (i18n)

Localisation packages for each ALA service are configured and deployed automatically, following the same mechanism as `ala-install`. Custom i18n overrides can be layered on top without touching the base packages.

### Branding

A dedicated branding container serves the CSS, JavaScript, and image assets that give the portal its visual identity. It is deployed first in the startup sequence, since all other services depend on it for their appearance.

Deploying a Living Atlas portal involves four repositories that work in concert. They form a clear hierarchy:

```
               │ produces

```

### `la-toolkit` — the top-level interface

[la-toolkit](https://github.com/living-atlases/la-toolkit) is a Flutter-based web and desktop application that sits at the **top of the operator workflow**. It is the entry point for managing a Living Atlas portal — operators never need to run generator commands or Ansible directly.

la-toolkit's responsibilities:

- Provide a GUI for all portal configuration decisions (which services, which machines, which URLs)
- Call `generator-living-atlas` under the hood when configuration changes, regenerating the inventory automatically
- Allow operators to designate machines as Docker Compose hosts and assign services to them
- Trigger Ansible playbook runs against the current inventory
- Monitor deployment status

**la-toolkit already supports Docker Compose** at the UI level. The minimal patch needed is to ensure that when running against a Docker Compose machine, la-toolkit invokes playbooks from `la-docker-compose` instead of from `ala-install` directly.

### `generator-living-atlas` — the inventory factory

[generator-living-atlas](https://github.com/living-atlases/generator-living-atlas) is a [Yeoman](https://yeoman.io/) generator that translates the decisions made in la-toolkit into concrete Ansible inventory files. It is the layer between the UI and the deployment automation.

It works **idempotently**: running it again on an existing configuration updates only what has changed, preserving all customisations. This makes it safe to re-run whenever the portal configuration evolves.

Docker Compose deployments are already partially supported. The key variables it produces include:

| Variable | Role |
| --- | --- |
| `LA_use_docker_compose: true` | Enables Docker Compose mode for this portal |
| `docker_extra_hosts` | Cross-host IP mappings for multi-machine networking |
| `nginx_docker_internal_aliases` | Domains this machine's nginx answers locally |
| `docker_mail_development_mode` | Switches between Mailhog (dev) and Postfix (prod) |

**Patch needed**: when `LA_use_docker_compose` is true, the generator must produce container names instead of `localhost` for database hostnames:

```diff
-collectory_db_host_address: localhost
+collectory_db_host_address: mysql
-ticket_registry_db_hostname: localhost
+ticket_registry_db_hostname: mongodb
```

## Development mode: running services locally

One of the most useful features is a **local development mode**: run one or two services on your laptop, while using a real live portal for everything else (authentication, species data, etc.). No need to stand up a full portal just to work on a single service.

### How it works

```
Browser → localhost/collections  →  nginx (local)  →  collectory container
Browser → localhost/cas          →  nginx (local)  →  proxy to auth.real-portal.org  (real CAS)
collectory container → auth.real-portal.org  →  resolved via docker_extra_hosts (real IP)
```

The service configuration points to the **real portal's CAS**, so authentication works against live data. The local nginx proxies unknown paths to the real portal, so links within the UI still work.

### Inventory structure

The inventory uses the `localhost.service` convention: the Ansible inventory hostname is `localhost.collectory`, but `ansible_host=localhost` tells Ansible where to connect. This gives each service its **own variable namespace** even though they all run on the same machine — without it, variables from different service groups would collide.

```ini
[docker_compose]
localhost.collectory                 ansible_host=localhost ansible_connection=local
localhost.cas-servers                ansible_host=localhost ansible_connection=local
localhost.branding                   ansible_host=localhost ansible_connection=local
localhost.bie-hub                    ansible_host=localhost ansible_connection=local
localhost.biocache-hub               ansible_host=localhost ansible_connection=local
localhost.namematching-service       ansible_host=localhost ansible_connection=local
localhost.gatus                      ansible_host=localhost ansible_connection=local
# ... enable only the services you need locally

# Service groups — required so roles can access group_vars
[collectory]
localhost.collectory

[cas-servers]
localhost.cas-servers

[branding]
localhost.branding
# ... one section per service
```

Developers simply comment out or remove the services they don't need locally — those paths are served by the real portal via the nginx proxy.

### Typical workflow

```bash
# Generate config for a single service only
ansible-playbook playbooks/config-gen.yml -i inventories/dev/ --limit localhost.collectory

# Start it
docker compose up -d collectory nginx

# Edit, restart, test, repeat
docker compose restart collectory

# Add another service later
docker compose up -d bie-hub
```

## Deployment order

Services must be started in a specific order to avoid dependency failures:

1. **SSL certificates** — nothing else can start without valid certs
2. **Branding** — required by all other services visually
3. **Infrastructure** — MySQL, MongoDB, nginx
4. **Database initialisation** — schemas, users, CAS setup
5. **CAS, User Details, API Keys** — authentication before protected services
6. **Collectory** — first functional end-to-end check
7. **Gatus** — monitoring active before deploying the rest
8. **Email** — needed for user accounts and alerts
9. **All remaining services**

## Testing strategy

Three levels of testing are supported:

| Level | Tool | What it tests |
|---|---|---|
| Local lint | `yamllint`, `ansible-lint` | Syntax and style |
| Local integration | Molecule (Docker driver) | Role logic, compose file validity |
| Real infrastructure | Jenkins pipeline | Full end-to-end on real machines |

The Jenkins pipeline automates the full cycle: clean machines, regenerate inventories, deploy, and validate. It can also be run in `CLEAN_MACHINE` mode to reset machines to a known state before testing.
